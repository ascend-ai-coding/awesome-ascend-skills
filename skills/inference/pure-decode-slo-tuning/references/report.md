# 纯 D 寻优报告结构与验收

参考 A5 10 ms 报告的“**三、纯 D 卡切分（假 KV 口径）**”结构。按事实填写，表格优先；让读者从第一页看到最优轮次和适用限制。不要把实验过程流水账放在总结论前。

## 报告顺序

1. **标题、环境与总结论。** 写硬件、镜像/版本、模型、数据集和日期。结论先给最高合规配置的 `cc / QPS / TTFT / ITL / 真实 AL / 折算 TPOT / 成功数`，标明这是短测还是全量；另给最终全量确认。写 SLO 公式、严格比较符号、成功率和资源上限。若短测 QPS 高于全量，分别列出样本范围，不做直接归因。
2. **3.1 方法与口径。** 表格列模型/切分、数据集 SHA256 和真实长度分布、完整 benchmark 命令关键参数、取数顺序、真实接受率样本数/逐位置 rates/AL、假 KV connector/fill、SLO、显存上限、每点请求数、完整确认规则。说明假 KV TTFT 的限制。
3. **3.2 切分对比。** 每个合法 DP×TP 的状态、canary、失败根因和恢复情况；明确固定非切分参数。
4. **3.3 MNS/MBT 并发爬坡。** 表格至少列 `MNS/MBT（及兼容性 HCCL 例外）、cc、请求数、成功数、QPS、输出 token/s、ITL P50、折算 TPOT P50、Running 最大、Waiting 最大、状态`。长表可移到附录，但正文要给各组合最高合规 QPS、相邻边界和胜出依据。MNS/MBT 与 HCCL 参数验证分清。
5. **3.4 配置参数验证。** 一次改单参数族；每项列最高合规 cc、成功数、QPS、ITL/TPOT、结论。投机配置另表列每种 K/采样法对应的真实 rates 和 AL、边界。失败/未测/仅固定 cc 对照要明示。
6. **3.5 实际可用容量。** 胜出配置、短测最高合规 cc/QPS/TPOT、相邻点、完整数据集确认；写监控采样数、活跃样本数、8-rank 抓取错误、Running/Waiting。
7. **3.6 无约束峰值。** 已测全部成功的最高 QPS、cc、TPOT 和是否违反 SLO，不能称“可用容量”。
8. **3.7 判断。** 结论限定在当前镜像/模型/数据/输出政策/SLO；不要宣称未测 TP 或未复核边界。写 P90/P99 时标明 SLO 是否只要求 P50。
9. **3.8 原始与最终脚本差异。** 只列影响核心启动配置或纯 D 测试口径的差异，不以 local IP、环境变量、端口、格式充数。若后续追加开关，另节列单开关/组合对照，保留原寻优和追加结果的时间顺序。
10. **复现实验材料。** 直接贴原始脚本、最终纯 D 脚本及所有必需的容器启动、数据准备、代理、benchmark、监控和接受率采样脚本**原文**；写镜像名/ID、模型名、数据集名/SHA256、运行顺序和所需输入。把 IP、网卡、模型/数据根目录参数化，不依赖单台 A5 的绝对目录。说明真实接受率脚本与假 KV 性能脚本用途不同。

## 表格与数字规则

- `TPOT Px = ITL Px / 固定真实 AL_K`，保留原始全精度计算，展示时适度四舍五入。标注 AL 的样本量；假 KV 实现 AL 不能替换分母。
- 每轮保存或链接原始 benchmark JSON、日志、启动日志、监控结果、精确启动脚本。报告中的 QPS、成功数、输出 token、Running/Waiting 要能从这些文件核对。监控缺失时写“未采集”，不能推定队列为 0。
- “合规”须同时满足声明的时延 SLO、成功率/超时要求和资源限制；启动失败与 OOM 不写成性能 0。对完整数据集必须核验行数和输出 token，不只看命令中的 `--num-prompts`。
- 对照表中的不同请求数或输出策略要显著标注，不能把 480 条筛选和 1000 条确认直接放在同一排名。变更后的脚本即使全量合规，未经独立爬坡也不能继承旧脚本“最高合规 cc”。
- 写明最终服务状态：正在运行且所有 endpoint 健康，或按用户要求已停容器且 NPU 无占卡进程。不要把历史恢复健康记录当作当前状态。

## 交付前检查

- 报告总结、表格、附录脚本的配置一致；最终脚本原文与交付的 `.sh` 文件一致，`bash -n` 通过。
- 原始脚本未被覆盖；数据集身份、镜像名和所有复现依赖明确；脚本在异机上不要求旧机器的目录/IP。
- 短测、全量、真实接受率与追加 A/B 的证据等级准确；失败和未测项目没有伪装成结论。
- 若用户要求停容器，先收集结果再停，并检查 NPU 进程；报告状态同步更新。
