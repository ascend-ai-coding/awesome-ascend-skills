# 纯 P 寻优报告格式与验收

使用一份**独立、可移植的 Markdown 文档**交付每次寻优。以表格呈现流程和结果；让读者先看到全量确认的最佳性能，再看到如何筛选。实验未完成时，在页首标明“进行中”，总结论写“尚未确认”，逐阶段追加已验证结果；不要把短样本领先值写成最终最优。

## 固定章节顺序

### 一、总结论

首段直接写适用范围：硬件与卡数、镜像 tag/digest、模型与量化、数据集及输出长度、SLO、成功率、资源上限、负载语义。随后用表格突出**全量最高合规轮次**：拓扑、关键启动参数、`rr`、`cc`、`np`、成功数、实际 QPS、TTFT 目标百分位及数值、prefix-cache 命中率、Running/Waiting 峰值。注明全量重复次数及结果范围；若只跑一轮，明确其证据限制。列出最接近的失败边界和被排除的候选。若还没有全量合规结果，不指定“最优”。

### 二、合同、环境与数据

用表格列：节点/卡型/卡数及占用检查、容器与镜像 ID、vLLM/vLLM-Ascend/CANN 版本、模型权重标识及 `config.json` 量化元数据、CLI 量化、原始脚本 SHA-256、数据集名称/版本/行数/SHA-256、实际输入 token 的 min/mean/P50/P90/max 与离群数、输出 token、temperature、`ignore_eos`、shuffle/order、thinking、请求超时、`rr`、`cc` 定义、路由/API 端口、prefix-cache 清理和随机预热顺序、TTFT 计算定义，以及**用户指定或确认的 SLO 指标/百分位/阈值/比较符号、成功率和资源限制**。若有文本化、多模态替换或抽样副本，单独列转换规则、行数、顺序及 SHA-256，写明是否经过用户同意。

给一张**流程总览表**：原始基线 → 固定参数的并行形态 → 每形态 cc 边界 → 胜出形态上的单参数族搜索 → 大样本复核 → 全量确认 → 最终服务验证。各行写测试规模、准入/淘汰门槛和原始结果入口。这样读者能看出每一步依据，而不必从日志猜流程。

### 三、固定参数的并行形态筛选

先列**形态阶段固定值**（至少 TP/DP/PCP 之外的 MBT、max-num-seqs、显存比例、block size、HCCL buffer、SWA、prefix cache、投机方法/长度、模型长度、API/headless 结构）。逐形态表列：TP/DP/PCP、API 进程数/HTTP 入口数、worker 数、实际启动及模型身份、真实长输入预热、失败根因、是否进入性能测试。PCP 等必需例外单列，不用不同 MBT 冒充固定参数形态对比。启动失败或 HTTP 500 不能记成 0 QPS。

对每个可用形态附 cc 爬坡表：`cc`、DP、`cc/DP`、`np`、`np/cc`、`rr`、成功数、实际 QPS、输入 token/s、TTFT P50/P90/P99/最大值、prefix-cache 命中率、Running 峰值、Waiting 峰值、合规判断。`cc/DP` 必须为正整数，`np/cc ≥ 4`；写出相邻达标/不达标点和最佳达标点的至少两次独立复测。比较各形态**各自最高确认合规 QPS**，另列无约束峰值而不称可用容量。

### 四、固定形态后的配置搜索

先列胜出形态和此阶段的共同基底。按参数族分表，至少覆盖适用的：max-num-seqs、max-num-batched-tokens（包括与输入上界相关的高档）、gpu-memory-utilization、block-size、HCCL_BUFFSIZE/通信、SWA bounded replay、prefix caching、DSpark 采样及方法、FlashComm1、EPLB/冗余专家，以及镜像实际支持的 MC2、MLAPO/weight layout、KV transpose、多流重叠、async/短请求调度、CPU binding/affinity/OMP、分配器和模型长度。每项列**基底值、试验值、启动和真实请求状态、各自最高确认合规 cc、np、QPS、TTFT、prefix-cache 命中率、Running/Waiting、结论与日志证据**。

每次只改一个参数族；候选必须在自己的 cc 边界重新爬坡。固定 cc 的短测只能叫“筛选”，不能直接宣称容量收益。对于无效参数，写明“镜像不支持”“运行时关闭”“该纯 P 路径不适用”或“未测试”及证据，不能把未生效配置写成 A/B 性能对比。相近结果用较大样本和独立重启复核；故障、OOM、超时、不可见 token 按合同原样记录。

在参数表前列出已确认的 MBT 及其大样本、重启稳定性证据。每个 EPLB 等下游参数对比都标明完整基底配置；最终 MBT、CPU affinity 等基底值若与测试时不同，列出在最终组合上的复测结果，否则明确标为“最终组合未测试”，不得用旧基底的结果作最终取舍或宣称全套参数寻优完成。

### 五、大样本、全量与最终服务

把短样本和大样本分表，列出同数据、同 `rr`/`cc` 口径的候选；全量表列每一独立轮次的 `cc`、`np`、成功数、QPS、TTFT 各百分位、prefix-cache 命中率、Running/Waiting、指标采样失败数、异常日志。全量必须覆盖用户指定数据集全部行；核验实际完成数与输出 token，而非只看命令参数。写清用户 SLO 的百分位和比较符号。若相邻更高 cc 失败或边界非单调，保留原始结果并解释选点。

最终部署脚本只从已测候选派生；列出部署时有意改变的值（例如关闭开发模式）。启动实际最终服务后，检查全部 API `/health`、`/v1/models`、真实长输入请求和一次足够规模的同口径确认；部署抽样与全量结论分开。记录**写报告当时**的容器/端口/NPU 进程状态；若用户要求停止服务，写明已停及核验结果。

### 六、原始与最终启动配置差异

用简表列影响性能或功能的核心参数：原始值、最终值、采用理由和对应实测轮次。IP、网卡、路径、端口、格式、为诊断开启的开发模式可在复现说明中列出，但不要拿它们充当核心性能差异。若使用 API leader + headless 等多进程架构，逐个说明哪个进程承载 HTTP、哪个承载 NPU worker；“一个 API 端口”不得写成“所有内部通信只用一个端口”。

### 七、归档与复现入口

直接写**镜像名和 digest、模型名及量化、数据集名称和 SHA-256、完整原始启动脚本原文、完整最终启动脚本原文**。若需 API/headless 双脚本、launcher、代理、数据转换器和压测脚本，提供其原文或可直接运行的完整命令与版本/哈希，写明启动顺序、环境变量和健康检查。把 IP、网卡、模型/数据挂载点写成目标节点需替换的变量；复现步骤不能依赖实验节点的私有绝对路径。给出精确的全量 benchmark 命令，含 `rr`、`cc`、`np`、输出长度、temperature、`ignore_eos`、shuffle/order、超时和缓存/预热协议。说明原始脚本未覆盖并给原始/最终脚本 SHA-256。

原始 JSON、服务日志、代理逐请求日志、每秒指标、失败轮次放在证据索引表中，可附本次实验路径；**路径表不能替代上述可移植复现内容**。

## 写作与验收规则

- 不混合不同镜像、数据集、输出策略、`rr` 或样本规模计算收益；用户改测试口径后，同协议重跑基线。
- 每个数字能回溯到原始 JSON 或逐请求日志。报告中的请求成功数须按合同逐条核验；可见首 token 与 HTTP/流/输出计数不一致时单列。
- TTFT/成功率、配置显存比例和用户要求的其他限制**同时**满足才称合规；观察到的 NPU 算力利用率与 `--gpu-memory-utilization` 分开写。
- Prefix cache 的测试前清理、预热顺序、同轮自然命中及实际命中率每轮留证；Running/Waiting 无数据时写“未采集”，不能猜为零。
- 原始和最终脚本正文与归档 `.sh` 文件一致，校验哈希，`bash -n` 通过；报告头部的最优参数与启动命令一致。
- 结论只覆盖已测硬件、镜像、模型、数据和 SLO；不把失败形态、未复核参数或单次短测写成已证实的全局最优。
