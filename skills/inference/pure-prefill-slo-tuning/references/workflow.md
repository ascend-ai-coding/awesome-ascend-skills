# Ascend pure-P SLO-constrained tuning

This is the complete workflow for a requested pure-prefill search. Optimize **confirmed QPS that satisfies the stated TTFT SLO and success requirement**. A healthy API, a short benchmark, or the largest passing client concurrency is not by itself a final result.

The A5/DeepSeek details below are **examples and conditional feature checks**, not defaults for another user-supplied model or image. Inspect the actual image and model before proposing topology or model-specific knobs; use only supported/applicable families and record why others were skipped.

## 0. Present a concrete plan and wait for confirmation

Use read-only inspection to prepare a reviewable plan before touching a live service or launching tests. Ask the user for, or locate and have them confirm, the **dataset and exact slice**, model/weight, image tag or digest, baseline startup script, node/card allocation, and benchmark contract: request format, temperature, `ignore_eos`, shuffle/order, output length, `rr` (including whether `inf`), timeout, SLO percentile/threshold, success definition, cache policy, and resource ceiling. Do not import a prior run's settings merely because the model name matches. If an image or dataset is absent, say so and resolve that before execution.

Show the user **the whole staged workflow** and a table of **actual startup parameters** before asking for confirmation. The table must give baseline values and planned candidate values or support checks for: topology (TP/DP/PCP, `--api-server-count`, `--headless`, API port/routing), `max-num-batched-tokens`, `max-num-seqs`, `gpu-memory-utilization`, `block-size`, `HCCL_BUFFSIZE`, SWA bounded replay, prefix caching, speculative method/token count and sampling, communication kernels, EPLB/redundant experts, and applicable extended knobs from section 4. Name the exact original script and separate variant directory, identify node-specific substitutions, and show the proposed `cc`/`np` ladder and final full-data run. State which candidates depend on image support and will be skipped only with evidence. Include expected service restarts and the rollback plan. The user should be able to approve the concrete plan without interpreting a vague list of parameter names.

Use two compact plan tables: **(1) stage / goal / proposed samples / pass gate**, and **(2) startup option / value in the user's baseline script / values to test / support check**. Populate the second table by inspecting the supplied script and image, not with remembered values from an earlier A5 run. Explicitly show the planned `cc = DP × k` ladder and `np ≥ 4cc` calculation for each topology or describe the exact rule that generates it within the available dataset size.

Wait for the user's confirmation **before** stopping a service, editing a live startup file, starting a variant, or running a benchmark. Prior explicit approval of the same plan counts; do not ask twice. If the user changes inputs or the load policy, revise the plan and re-establish same-protocol baselines before ranking. Keep read-only inventory and script preparation separate from live execution.

## 1. Freeze the experiment contract

Record before launching candidates:

- A5/A3 hardware, node and available card count; exact image tag and digest, engine version, model weight identity, model `config.json` quantization metadata, CLI quantization, and the startup script actually used.
- Dataset identity and hash, input-length distribution, output length, request count, temperature, `ignore_eos`, shuffle/order, thinking mode, warmup, timeout, client load model (`rr` and `cc`), seed, routing across service ports, and prefix-cache policy.
- TTFT definition and behavior for invisible/special tokens, percentile and threshold, required successful-request fraction, timeout policy, and any resource ceiling. Distinguish benchmark TTFT from time to the first **visible** output token; distinguish configured `--gpu-memory-utilization` from observed accelerator compute utilization.
- Fixed topology-phase values: model length, MBT, mns, memory fraction, block size, HCCL buffer, speculative method/count, SWA, prefix cache, communication switches, and port group.

For a rerun of the A5 case that established this procedure, the supplied contract was **output 1 token, TTFT P50 <= 7 s, 100% successful requests, per-request timeout 120 s, and `--gpu-memory-utilization <= 0.95`**. Use those values only when the user asks to reproduce that case or confirms them for a new run. Never silently transfer its SLO or dataset to another workload.

Inventory card occupancy and ownership before claiming a node. Do not stop or remove another user's workload without authorization. Preserve the original launcher and startup scripts with hashes; create a separate experiment directory, one script variant and startup log per candidate, and a known-good rollback variant. Modify only the copies. Keep result JSON/stdout and failures. A retry on a different port or after a clean restart is a **new recorded attempt**, not a silent overwrite.

Verify the exact launcher file and hash used by the running service, especially when the user supplies a replacement `launch_online_dp.py`. Copy it to the experiment area before starting variants. Replacing a file on disk does not change an already-running service; confirm a restart and its process arguments/logs before attributing results to the new copy.

## 2. Profile the dataset and make measurements comparable

Read every dataset record once for a profile: row count, hash, fields, prompt uniqueness, prefix metadata, token-length min/mean/P50/P90/max, and counts outside any named length band. A dataset called "20k-40k" is not proof every record lies in that range. Do not filter outliers or replace the dataset without authorization. Check both file token metadata and service-reported `prompt_tokens` on measured requests. Override source `max_tokens` with the agreed output length when needed.

Use the same request payload, model name, deterministic sample order/seed, port routing, timeout, and concurrency semantics for all candidate comparisons. Preserve the user-supplied temperature, `ignore_eos`, shuffle/order, output length, and thinking mode. Inspect an **actual outgoing request** to confirm these values reached the service; benchmark flags or dataset fields alone are not proof. State whether `rr` is finite or `inf`; `rr=inf` removes rate pacing but does not remove the client `cc` cap. Verify the installed benchmark's actual arrival and concurrency behavior rather than inferring it from option names. Define success exactly as agreed: some runs require a visible first token, while others count HTTP 200 + complete stream + intended output-token count and separately report invisible output. Never silently change the user's success rule or omit the visible-token count and TTFT interpretation.

For each independent service startup, check **every** expected `/health` endpoint and `/v1/models`, then run real long-input requests as warmup. Health alone does not prove a topology can infer. If prefix caching is enabled and the workload requires comparable cache state, verify `reset_prefix_cache` actually works. Follow the agreed order precisely: for example, reset once before each round, then send random long-input KV warmups and **do not reset a second time** when that is the contract. If reset is unavailable, use an agreed KV-flush method or clean restart and record the difference. Record natural same-round prefix hits separately from cross-round contamination. Capture the prefix-cache hit ratio for each round and put it in the report, even when it is not a winner metric.

Measure duration, completed/failed, QPS, input-token throughput, TTFT P50/P90/P99/max, offered `cc`, peak service `Running` and `Running+Waiting`, and abnormal startup/runtime logs. Keep raw per-request and sampled service metrics. If a remote shell hangs after the benchmark has written its result, verify the complete JSON and process state rather than assuming a failed or completed test from terminal behavior alone.

## 3. Establish a baseline, then search legal topologies

At fixed baseline parameters, get a real-request baseline and bracket its SLO boundary. For an 8-card image, search only topologies supported by the **running image, model, and launcher**. TP1/DP8, TP2/DP4, TP4/DP2, and TP8/DP1 are useful candidates when supported. The `v0.32.0rc1-a5-openeuler` 950DT guide also documents an **experimental PCP8 Prefill** branch; test it separately after adapting the DP1 launcher and checking actual long-input requests. Do not assume a documented topology works or omit one because an earlier scan did not include it.

For each topology, first attempt the **same baseline MBT and other non-topology limits**. This includes PCP candidates: use their required topology-specific launcher/configuration, but try the baseline MBT before tuning it upward. If a topology cannot start or serve real long requests at that MBT, preserve the exact failure and label any higher-MBT result as a conditional follow-up, not a fixed-parameter topology comparison. In particular, PCP8 at MBT 16k or 32k does not answer how PCP8 compares with TP1/DP8 at MBT 5120.

For each topology:

1. Start from its isolated script with all non-topology values fixed. Check worker startup, all expected ports, model identity, and several real long-input requests.
2. If startup fails because a port is occupied, compare the fixed port with the host ephemeral range and retry the **same** configuration on a non-overlapping free port group before attributing the failure to topology. Classify kernel/quantization/shape errors separately. A topology that starts but fails real requests is unusable; neither case is "0 QPS".
3. For a valid topology, ramp offered `cc` coarsely, then refine to adjacent passing/failing points under the exact SLO. Repeat the chosen passing point at least twice, and inspect nearby lower passing points when QPS is flat or noisy. Record actual Running/Waiting so a client or connector cap is visible.
4. Rank valid topologies by confirmed **SLO-compliant QPS**, not raw peak QPS or maximum `cc`. If all alternatives are invalid, record the evidence and say that no runnable runner-up exists.

At every `cc` ramp point, choose `cc = k × DP` for a positive integer `k`; DP means actual data-parallel replicas, **not** API-server process count. Use `np ≥ 4 × cc` submitted prompts for that point, including screening rounds. For fixed datasets, limit the largest `cc` so the dataset supports this; do not silently duplicate rows to inflate `np`. Advance in DP-sized increments near the boundary and retain the nearest failing point. With `rr=inf`, the concurrency ladder is the load axis; changing from finite `rr` to `inf` invalidates direct capacity ranking from earlier rounds and requires a fresh baseline.

The A5 reference fixed MBT 5120, mns 16, memory 0.90, block 128, `HCCL_BUFFSIZE=1024`, SWA on, and DSpark 5 greedy for topology comparison. Its TP2/DP4 and TP4/DP2 failed real sparse-MLA requests; TP8/DP1 failed weight-scale initialization. Recheck these behaviors on a new image instead of carrying over the exclusions.

## 4. Search parameters on the selected topology

Keep the workload and selected topology fixed. Change one parameter family at a time, restart cleanly, warm up, verify the effective feature, and **re-search its passing `cc` boundary**. A fixed-cc throughput difference is insufficient to select a value. Use common samples for first-pass comparisons, repeat close results, then promote promising candidates to larger samples.

When claiming a parameter's gain, compare runs with the same dataset slice, request count, load semantics, and compatible `cc`; do not compute an improvement percentage by mixing a short screening run with a full-dataset run or by attributing different-cc QPS to a single knob.

**Freeze the core baseline before secondary feature tests.** Sweep MBT first on the selected topology while other settings are fixed. Re-bracket each viable candidate's SLO-compliant `cc`; promote close candidates to the same larger sample and repeat after an independent service start when practical. Confirm request success, TTFT, completed throughput, long-input stability, and worker health. A short-sample lead or a stalled larger run does not establish the winning MBT. Record the chosen MBT and its evidence before testing `max-num-seqs` and secondary features such as EPLB, CPU affinity, communication, and cache/replay. Record the full baseline configuration for each comparison, not just the changed flag.

If a later test changes MBT or another baseline setting, treat all dependent comparisons on the old baseline as provisional. Re-run the relevant shortlisted feature on/off comparisons, especially EPLB, against the **actual final combination** with the same dataset slice, load semantics, cache policy, and other settings. Re-find `cc` boundaries and verify feature activation (including expert migration for EPLB). A result measured only at an earlier MBT cannot establish that the feature helps or hurts the final MBT. If a required retest is missing, label it "untested on the final combination" and do not claim that the parameter search is complete.

| Family | Required check and decision rule |
| :--- | :--- |
| `max-num-batched-tokens` (MBT) | Sweep below and above baseline, and extend the upper side to values relevant to the dataset's long prompts. For 20k–40k inputs, do not stop at 16k: include a TP/DP-matched candidate around 32k and consider a value above the upper input band (for example 48k) when startup and memory permit. Choose levels from the actual length distribution on other datasets, not these fixed numbers. Check startup and real long-input inference first, then compare each viable value at its own SLO-compliant load boundary; promote close candidates from short samples to a larger sample and full data. Keep model length and other limits fixed. Record any unsupported, OOM, AICore, or stalled attempt as the reason for stopping the upward sweep. A high MBT result from PCP does not substitute for testing it on the chosen TP/DP topology. |
| `max-num-seqs` (mns) | Test values on both sides of baseline at the selected MBT; re-bracket `cc`. Compare at matching load when attributing small differences. |
| `gpu-memory-utilization` | Test within the user's ceiling, never above it. Record KV-cache capacity, startup safety, SLO-compliant QPS, and observed memory. More reserved HBM need not improve throughput. |
| `block-size` | Recheck success on a larger sample. One empty/invalid streamed response disqualifies a candidate under a 100% success requirement even if its QPS looks competitive. |
| `HCCL_BUFFSIZE` and communication settings | Verify worker startup and real requests before measuring. Preserve tiling/window-size failures as invalid attempts; distinguish retryable port conflicts from configuration failures. |
| SWA bounded replay | Test enabled and **truly disabled** with the correct positive/negative flag for the image. Confirm the effective value in runtime logs or process configuration. Do not infer an ablation from a changed script alone. |
| FlashComm1 and other named kernels | Inspect whether the exact image supports the feature and whether logs say it remained enabled. "Accepted config, then disabled" is unsupported for this comparison; do not publish an ineffective A/B QPS. |
| DSpark sampling, including `draft_sample_method=probabilistic` | Verify the option and whether draft/accepted-token counters are active on the pure-P output-length workload. With output 1 token and no draft activity, report no applicable performance effect rather than crediting sampling. |
| Prefix cache | Fix its on/off state in normal candidate comparisons and reset policy in measurements. Test a cache ablation only when it is part of the requested search; use a repeated-prefix workload to study cache benefit. |

This is an **applicability checklist**, not a requirement to run unsupported flags. For every family, record tested values, passing and failing boundaries, repeated QPS/TTFT, startup or request failures, and the evidence for "unsupported" or "not active." Do not stop after MBT and mns. Re-run a valid topology runner-up under final parameters when one exists; otherwise explain why that interaction check was impossible.

For an official-parameter extension, audit the exact image tag's model guide and configuration guide against the installed implementation. Check additional Prefill families when applicable: EPLB and redundant experts, MC2 communication algorithm, MLAPO and weight layout, KV transpose, model/sequence length limits, multistream overlap, async and short-request scheduling, CPU binding/affinity/OMP, and allocator settings. Verify EPLB has actually migrated experts before its steady-state measurement; repeated warmup prompts may hit prefix cache and must not be ranked as throughput evidence. Keep a tested/unsupported/inactive reason for each family instead of treating an accepted but inactive flag as a performance result.

## 5. Promote short scans to a final result

Use staged sample sizes: a common short sample to screen, a larger fixed sample to confirm close candidates and neighboring `cc` values, then the **entire specified dataset** for the chosen configuration. Scale counts to the dataset and selected `cc`, ensuring `np ≥ 4 × cc` **at every ramp point**; never call a short scan "full-data validation." Keep seed and sample selection fixed. A final full-data `cc` above `floor(dataset_rows/4)` requires an agreed repeated-data protocol or a lower `cc`.

The SLO boundary can move with sample length or service restart. Re-bracket on the larger sample; repeat the intended passing point, test its nearest higher point and a lower passing point when QPS is flat. Select the compliant point with the highest confirmed QPS; if adjacent `cc` values have indistinguishable QPS, prefer the one with more latency headroom. For a final production recommendation, seek independent cold-start confirmations when practical. If the full dataset was run only once, state that limitation and avoid statistical-significance or global-optimum claims.

The full-data run must finish with the required success fraction, measured TTFT under SLO, no unresolved AICore/worker failures, and recorded throughput plus Running/Waiting. Do not count a failed request as a completed TTFT or a startup failure as zero throughput. Tail percentiles may be informative but do not silently change a P50 SLO into a P90/P99 gate.

## 6. Validate the actual final service and handoff

Create the deployment script from the tested candidate **without changing the tuned core parameters**. Record any intentional deployment-only changes, such as disabling dev mode and binding the service address. Confirm the original files' hashes are unchanged and show a diff between original and final startup scripts. Start the final service, check all endpoints and model identity, send real warmup requests, and run a substantial confirmation sample against that actual service. Leave the requested working service running; preserve rollback scripts and logs. Do not delete another user's containers or storage as part of cleanup.

Write the independent, table-first report using [report.md](report.md). It must include the full original and final startup scripts, exact benchmark command and data conversion, a node-independent reproduction recipe, raw-result evidence, and a current service-state check. Do not substitute a path-only archive table for the information needed to reproduce.

The A5 run used prefix-cache reset for measured tuning rounds, then a non-dev final service without that reset endpoint; its final-service sample passed the same SLO. This is a useful deployment parity check, not a license to mix results from different datasets or sample sizes.
