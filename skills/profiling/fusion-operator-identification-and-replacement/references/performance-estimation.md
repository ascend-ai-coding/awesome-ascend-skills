## 1. 预测的两类与置信度三级

| 类型 | 定义 | 依据 | 报告标注方式 |
|---|---|---|---|
| **理论估算** | 用计算模型（访存量÷带宽、FLOPs÷算力、launch 次数×开销）从第一性原理推导 | 本文 §2–§4 | "理论估算" + 假设清单 |
| **经验预测** | 用同类替换的历史实测数据外推 | 历史数据（用户提供，或可信公开来源且注明出处）+ 场景差异说明 | "经验预测" + 数据来源与差异 |

置信度分级（写进候选清单的"预测可信程度"字段）：

- **高**：有目标硬件上同类融合的实测数据，且 shape / dtype / 场景接近
- **中**：有用本份 Profiling 反推出的实测带宽 / 算力 / launch 开销做标定，计算模型明确
- **低**：只有峰值参数或数量级假设——此时**给区间，不给单点值**

**没有数据就没有数字。** 数据不足时二选一：

- (a) 条件化估计："若有效带宽为 X GB/s，预计节省 Y（区间），置信度低"
- (b) 列出需要补充的数据清单，明确说明没有这些数据无法估计

禁止给出无依据的加速比。

## 2. 基础计算模型

### 2.1 访存量

```
bytes(tensor) = Π(shape 各维) × dtype 字节数     （忽略对齐/填充，是下界；注明）
单算子理想 HBM 流量 = Σ(输入读取) + Σ(输出写出)
```

### 2.2 融合省下的流量

```
ΔB = Σ 被消除中间张量的 (写 + 读) 字节 + 被消除的 TransData 流量
```

注意：中间张量若被融合体外的分支消费，那次写出省不掉，ΔB 里不能计。

### 2.3 融合后耗时下界（Roofline 形式）

```
T_fused ≥ max( (Σ输入读 + Σ输出写) / BW_eff ,  FLOPs / FLOPS_eff ,  t_launch )
```

- BW_eff、FLOPS_eff **不要用手册峰值**——用 §3 的标定值；实在没有就用峰值 × 50%~80% 折减系数，并声明这是假设（置信度降为低）
- max 由访存项主导 → 融合算子是访存受限的，收益估算按带宽做
- 小 shape 场景 t_launch 主导 → 收益主要来自 launch 次数减少

### 2.4 预计节省与端到端加速比

```
ΔT ≈ T_seq(时间线实测，含 kernel 间隙) − T_fused_est
端到端加速比 ≈ T_step / (T_step − ΔT)        （ΔT 必须在关键路径上，否则打折或为 0）
```

- T_seq 取**时间线上该序列的 wall time**（含 kernel 间空隙），不是各 kernel duration 简单相加——间隙部分在融合后也可能被消除（launch 减少）
- 但多流重叠的时间不能重复计入；序列若与通信流重叠，ΔT 要按未重叠部分打折
- **加速比必须同时给出序列级与端到端两个口径**，防止只报好看的序列级数字

## 3. 标定：从这份 Profiling 里取真实参数

这是让估算可信的关键——参数尽量取自实测而非手册：

- **BW_eff（有效带宽）**：从数据里挑几个大 shape 纯访存型 kernel（Add / Mul / Copy / Reduce），`BW_eff = bytes / duration`，取中位数。这些 kernel 已经跑出了该机器的真实带宽水平。
- **FLOPS_eff（有效算力）**：从大 GEMM kernel 反推 `2×M×N×K / duration`。
- **t_launch（下发开销）**：用小 shape kernel 的时间线间隙中位数估计（上界），或做一次极小 shape 的对照实验。
- **单位统一**：确认 duration 单位（us/ns）后统一换算，再代入公式。

如果数据里没有合适的 kernel 可反推（例如全是小 kernel、无 shape）：

- 带宽/算力只能引用官方规格（以 `ascend-operator-reference.md` §2 的硬件数据手册为准，**不要凭记忆填数**）并乘 50%~80% 折减系数给区间
- 置信度记为"低"，明确写出折减系数是假设

## 4. 完整算例（演示输出格式）

> 下例数字全部为**演示值**，用于展示输出格式；真实分析必须代入用户数据。

设时间线出现未融合序列 `Add → RMSNorm 展开(Mul, Rsqrt, Mul, Mul)`，shape `[token_num, hidden] = [4096, 4096]`，BF16。序列 wall time 实测 410 us（Add 90 us + 归一化链 320 us）。同一份数据中大 shape Mul kernel 反推 BW_eff = 1.2 TB/s。

```
每张量字节数 = 4096 × 4096 × 2B = 32 MiB

未融合流量 ≈ Add(读2写1) + RMSNorm链(读1写1，weight 小张量忽略)
           = (2+1+1+1) × 32 MiB = 160 MiB
融合后流量（AddRmsNorm：读 x、residual、weight，写 out[+residual_out]）
           ≈ 3~4 × 32 MiB = 96~128 MiB
ΔB ≈ 32~64 MiB

T_fused ≥ 96 MiB / 1.2 TB/s ≈ 84 us（下界，未含 launch 与 tiling 损失）
ΔT ≈ 410 − 84 ≈ 326 us（序列级约 3~4 倍，理论估算）

端到端：若该序列占 step 时间 2%，
step 加速 ≈ 1 / (1 − 2%×(326/410)) ≈ 1.02 —— 序列内收益大，端到端收益约 2%，需权衡工程成本
```

输出时**保持这个展开格式**：公式 → 代入 → 结果 → 假设（含折减系数、shape 来源）→ 置信度。算例必须明确标注"演示数字"。

## 5. 误差来源（报告中逐项声明适用了哪些）

- 折减系数假设（50%~80% 区间本身带来 ±30% 级别不确定性）
- tiling 与 UB 复用率：分块不理想时实际流量大于理想流量
- 小 shape 下 launch 主导，纯带宽模型失效（要切换到 launch 模型估算）
- 多流重叠：省下的时间不在关键路径 → 端到端无收益或收益打折
- Profiling 本身的开销使基线偏高 → 收益被高估
- 融合引入的新开销：入口/出口布局转换、原子操作、同步、额外寄存器/UB 压力导致的并行度下降
- 经验预测的适用性：历史数据的硬件/版本/shape 与当前场景的差异

## 6. 实测验证方法

验证方案在建议阶段（报告第 9 节）就要写清，实施后照此执行：

1. **算子级 microbenchmark**
   - 融合算子 vs 原序列，相同输入，覆盖边界 shape（min / 典型 / max）与动态 shape 区间
   - 预热若干次后测 N 次（建议 ≥100），报中位数与 P90，标注方差
   - 计时用 device 侧事件（如 aclrtEvent 或 profiler 时间线），不用 host 计时
2. **端到端验证**
   - 固定模型、固定输入与 batch/seq 配置；prefill 与 decode 分开测
   - 指标：吞吐（tokens/s）、首 token 时延、每 token 时延
   - 把实测 ΔT 回填到估算模型，标注预测偏差（校准下次估算）
3. **精度验证**
   - 与未融合实现对齐：按 dtype 定 atol/rtol，或逐层余弦相似度
   - 端到端：小规模评测集分数对比（验收线由用户定义）
4. **回归项**：shape 覆盖测试、量化模式开关组合、多卡/多 stream 场景

## 7. 红线回顾

- 理论数字不得写成实测结果；所有预测带"理论估算 / 经验预测"标签
- 无带宽/算力标定、无历史数据时，不给具体加速比——只给区间或定性判断 + 补数据清单
- 加速比必须同时给**序列级**与**端到端**两个口径
- 不得将 Profiling 中的算子耗时直接当成替换后的可节省耗时——ΔT 永远经过 §2.4 的估算流程
